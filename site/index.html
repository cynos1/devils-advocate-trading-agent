How it works

Reason creatively. Execute conservatively.

The model can recommend, criticize and revise. It cannot increase its own authority, bypass hard limits, or force a trade after repeated disagreement.

Market + Portfolio

Account state and eligible options form the bounded decision context.

Proposer Model

Chooses strategy, contract, size and rationale.

Devil’s Advocate

Challenges liquidity, assignment risk, concentration, expiry, premium and more.

Deterministic Risk Gate

Enforces sizing, collateral, exposure, daily limits, kill switch and fail-closed behavior.

Fresh Execution Check

Re-reads broker state immediately before any order submission. Final outcome: execute or NO TRADE.

Alpaca implementation

Three tools. Three jobs.

The project deliberately separates what the model can see, what can execute, and how the outcome is independently verified.

MCP Server

Research / Context

Model-facing access to account state, market data, options chains and research context. Read-oriented by design.

Trading API

Bounded Execution

Paper-order submission only after adversarial review, deterministic validation and a fresh execution check.

CLI

Independent Audit

Pre/post snapshots of account, positions, orders and market clock. The agent does not audit itself.

Evidence

When both models miss something, code still catches it.

One observed dry-run episode demonstrated why the deterministic layer exists: the proposer asked for four contracts, while the hard limit was three.

proposer → 4 contracts
adversary → concern, but sizing issue not caught
revision → still 4 contracts
second review → sizing issue still not caught
deterministic gate → safer code-generated substitute: 2
fresh execution check → PASS
outcome → DRY RUN, no broker order

Why this matters

The project does not assume the models will always be right. It assumes they will sometimes disagree, misclassify a risk, or propose too much size — and designs the execution layer accordingly.
